# Inherited runtime contract

Apply the applicable state and product row before choosing a comparison, advantage, transition, platform bet, test, or branch.

## State gates

- **Survival first:** If default-dead or time-to-zero binds, `managing-runway-and-survival` owns scenarios, deadline, and switch date. A competitive experiment may compose only when its result can change that plan within the available runway.
- **Learning first:** Until one target segment demonstrates real use, payment, or an equally discriminating commitment defined in advance, `learning-from-users` owns the need, sample, evidence standard, collection, and interpretation. Renewal or signed deployment qualifies only when it meets that same predeclared discriminating standard. Positioning may retain named alternatives and switching questions for that plan; it must not prescribe broad surveillance or a moat. Return only `State/ownership: learning-first`; `Primary owner: learning-from-users`; verified evidence; one narrow user/problem hypothesis; retained alternatives/dependencies; a dated observation/commitment gate; and ordered `Handoffs:` to `learning-from-users` for evidence and interpretation, `acquiring-and-growing-users` for recruitment execution, `shipping-and-iterating-products` for prototype exposure, and `competing-and-positioning` only after the gate for relative comparison. Then stop.
- **Positioning active:** Use this skill when user value is anchored and a real alternative, relative capability, incumbent response, transition, platform dependency, or platform/product-ecosystem creation decision changes the outcome. For platform creation, apply the learning gate to the core product, not to the proposed complement: paid use, renewal, or an equivalent discriminating core commitment makes positioning primary even when complement evidence is unknown.

Record an as-of date. Separate verified fact, bounded inference, unknown, and historical analogy. Revalidate any controlling platform term, API access, data portability, developer economics, library or labor supply, switching cost, distribution concentration, infrastructure or manufacturing cost, buyer behavior, incumbent capability, IP law, competition law, and sector regulation.

## Product rows

- **Capital-light software:** Reversible release and use evidence can reveal relative velocity in days or weeks. Cheap iteration does not apply when software controls money, identity, safety, trust, or irreversible outcomes.
- **Enterprise/integration:** Include procurement, security, interoperability, implementation, deployed references, switching, approval, and evidence latency. A benchmark, compliment, undeployed pilot, or self-serve signup is not committed substitution.
- **Hardware:** Recompute the enabling stack and include fabrication, reliability, inventory, certification, channel, physical use, developer complements, working capital, and current component economics. Do not impose weekly software cadence.
- **Biotech, energy, capital-heavy:** Use scientific, regulatory, infrastructure, safety, partner, financing, and specialist-buyer milestones. Do not default to race-ahead, early-software patent, or quick imitation tests.
- **Marketplace/community:** Positioning owns external alternatives, external platform dependency, and ecosystem competition. Growth owns cold-start liquidity and acquisition. Governance owns ranking, reputation, moderation, abuse, trust, transparency, and interaction quality inside the startup's network.
- **High-harm/regulated:** Require current law, permission, assurance, monitoring, rollback, human review, bounded exposure, incident response, and accountable user effects. Secrecy, speed, first-mover advantage, or incumbent pressure never overrides safety or truthful conduct.

## Decision predicates

### Rival attention and comparison

Begin a comparison only for an observed alternative, switching constraint, shared scarce user resource, capability gap, or credible response risk. Compare the predecessor problem fixed, user outcome, target, tradeoff, distribution, and control before features. Prefer working behavior, actual adoption, specific capability or hiring evidence, current lead, and relative development velocity over competitor count, publicity, funding, inherited reputation, or fear.

Select `use-competitor-evidence` only when the evidence changes the user thesis, alternative map, switching constraint, capability gap, or response plan. Otherwise select `stop-rival-surveillance`. Time-box any post-gate scan and cover mechanism, target user, tradeoff, distribution, and control. Route affected-user research through `learning-from-users`; positioning owns the competitive inference. Do not copy a surface feature or price reflexively.

### Advantage maturity

Use the chain `mechanism -> startup capability -> user-visible outcome -> observed commitment effect -> copy barrier -> continuing refresh`.

- Missing mechanism or effect: `unsupported`.
- Plausible effect without behavior change: `positioning-hypothesis`.
- Observed effect without disproportionate copy cost: `observed-advantage`.
- Observed effect, concrete integrated or ecosystem barrier, and continuing extension: `defensible-system`.

Difficulty without user value is cost. Patents and secrecy are stage- and category-dependent supports, not proof. Limit secrecy to lawful implementation detail; current legal conclusions require qualified current advice.

### Incumbent and transition

For incumbents, distinguish present power from historical shadow. Test installed distribution, ability and incentive to copy or bundle, development velocity, self-cannibalization, architecture, policy, culture, builder movement, and whether acquired innovation survives. Treat response as a hypothesis: `ignore`, `copy`, `bundle`, `block`, `acquire`, `litigate`, or `unknown`.

For transitions, require: a current constraint, scarcity, toll, or cost curve changed; users, capable builders, applications, or useful complements moved for more than promotion; and the entrant's economic or capability trajectory can reach the target use. Classify the change as complement, substitute, or new basis of competition. Record buyer switching constraints; entrant and incumbent incentives; and the durability of workflow, data, integrations, trust/compliance, distribution, and learning loops. Mark each item observed, inferred, unknown, or historical.

Before claiming substitution, test end-to-end cost and quality, workflow outcome, affected-segment usage, renewal/loss, and willingness to switch. For low-end entry, test continued improvement. For modularization, test supplier maturity, replaceability, customer ownership, and coordination cost.

### Platform dependence or creation

When dependent, record channel concentration, critical APIs, identity, billing, policy control, direct user relationship, data portability, switching cost, revenue share, technical constraints, policy timing, and migration rehearsal. Do not increase or make exposure irreversible without a credible dependency, policy, direct-user, portability, migration, and exit plan. Existing leverage may continue only inside a bounded platform pilot while those facts, alternate channels, and restricted-API replacements are tested.

For a compound external-platform decision, use a separable portfolio: keep each applicable portability, direct-user or direct-buyer, alternate-channel, restricted-API replacement, end-to-end substitution, and voluntary-builder-loop test separately named, bounded, and independently adjudicable. One shared exposure may cover several only when every hypothesis, action, metric, and readout remains separately adjudicable.

When building a platform, compare the current manual/status-quo path, an integrated-core feature, independent specialist or complement tools, platform-native alternatives, and the other work competing for the same user resource. Require capable builders to choose a product that is good enough to use, exposed capabilities that create unplanned value, and useful complements that pull demand. Openness, private ownership, or delayed monetization alone is not an ecosystem signal.

Before the platform-creation readout, actually execute removal/rollback. Do not hold the readout until that rollback test's own record verifies both that the core product works and that the direct customer/user relationship remains unharmed. A documented capability, global assurance, access check, or future removal assignment is not a tested rollback.

Treat platform creation as an executable action family, not merely a label. Precommit every row below with its own observable condition, date, operational person, `competing-and-positioning` decision owner and decision-recording action, plus ordered specialist handoffs with each exact named-skill owner and first action. A global list does not satisfy an outcome record.

- `keep-integrated`: require the test already to establish both a validated need that belongs in the core product and failure of independent complements to demonstrate value. Decision owner/action: `competing-and-positioning` records the decision. Ordered specialist handoffs: `shipping-and-iterating-products` removes/rolls back trial exposure; `engineering-for-leverage` retires interface work; `learning-from-users` reconfirms the affected need and segment before integrated shipping. Do not select this branch merely because learning can validate the need later.
- `expose-bounded-interfaces`: require useful recurring complements within the safe surface while at least one of broader pull, repeatability, governance, support, or economics remains unproved. Decision owner/action: `competing-and-positioning` records the bounded decision. Ordered specialist handoffs: `shipping-and-iterating-products` retains only revocable exposure; `engineering-for-leverage` hardens only the bounded interface; `learning-from-users` names and closes each evidence gap.
- `expand-ecosystem`: require all of repeat capable builders, recurring user value, complement-attributable demand, and a credible governance and economic path. Decision owner/action: `competing-and-positioning` records the decision. Ordered specialist handoffs: `learning-from-users` first names and closes residual evidence gaps. Before broader exposure, `governing-platforms-and-communities` first defines access, review, abuse, incident, and appeal rules and `designing-business-models` first tests developer/store pricing, support cost, and complement economics; then `engineering-for-leverage` first hardens approved interfaces and `shipping-and-iterating-products` first gates the release. Only after those gates does `acquiring-and-growing-users` first own builder adoption and user-side liquidity.
- `stop-platform-bet`: require failure to complete the builder-user loop, absent complement value, or a breached exposure/support/harm limit. Decision owner/action: `competing-and-positioning` records the stop decision. Ordered specialist handoffs: `shipping-and-iterating-products` first removes/rolls back exposure; `engineering-for-leverage` records and retires the failed interface; `learning-from-users` validates any remaining integrated-product need before shipping.

Use exactly these four action outcomes and apply precedence: any breached exposure, support, or harm limit selects `stop-platform-bet`; otherwise absent complement value plus a validated core-owned need selects `keep-integrated`; absent value without that core predicate, or an absent builder-user loop, selects `stop-platform-bet`; observed recurring value with safe reversible exposure but an unresolved prerequisite selects `expose-bounded-interfaces`; only every expansion predicate selects `expand-ecosystem`. Do not add an `inconclusive` branch.

Every material test locally repeats its operational person, baseline, bounded exposure, metric, confounders, date, disconfirming signal, preserved option, and observable pass/change/stop condition; global prose cannot fill a test-local field. A shared exposure may cover several tests only when every hypothesis, action, metric, and readout is independently adjudicable.
